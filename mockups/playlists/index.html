Saved playlists — three ways in

All three assume the same thing underneath: a playlist is a named, ordered list of hand-picked events, stored per account in the sheet, able to span games and filters freely. What differs is how events get into one and where a playlist lives in the Event Viewer. Every frame is live — tap around.

A · Row ＋, Playlists sheet

Every event row grows a ＋ at its right edge. Tapping it opens a short “Add to…” sheet. Playlists themselves are a fourth bottom sheet next to Game / Filter / Moves, and picking one swaps the event list for it.

  • Smallest change — one more openSheet kind, no new mode.
  • Add and play are always available; nothing is modal.
  • Costs ~40px of row width on a phone, permanently.
  • Two taps per event. Adding 30 backdoors is 60 taps.

B · Collect moderecommended

A ＋⃞ toggle in the filter bar turns the list into selection mode: rows tick instead of playing, a purple tray keeps the running count, and a pinned bar commits the lot at once. The selection survives a filter change — that is what makes “spans different filters” one save instead of many.

  • Filter → “All 12” → save. Bulk is one tap, not thirty.
  • Rows keep their full width when you’re not collecting.
  • A mode: you can’t play an event while collecting.
  • Needs the tray to explain itself the first time.

C · Playlist as a source

Playlists sit in the game picker above the games — one list of things you can watch. Picking one recolours the topbar and makes it the event source. A ⠿ button opens rename / reorder, and “add more events” arms the playlist so tapping ＋ on any row in any game drops straight into it.

  • Reorder gets a real home; prev/next works untouched.
  • Playlists feel equal to games, not a side feature.
  • Biggest change: picker, topbar, an armed strip, an edit screen.
  • Armed mode is sticky state that’s easy to forget you’re in.

What is identical in all three

A _playlists tab in the control sheet, one row per playlist (Id | Secret | Name | Note | Event Refs | Updated At), with Event Refs holding the ordered list of game#time#type#name refs the viewer already synthesises in evId(). Reads come back with action=all’s sibling action=playlists; writes are a save_playlist / delete_playlist post, scoped to the caller’s secret the same way canSeeGame scopes games today. Selecting a playlist replaces shown, so prev/next, loop, the scrub marks and the playback window all keep working with no change.

The one real risk

Event refs are synthetic, not stored IDs. An admin renaming an event in the Event Editor changes its ref and silently breaks the playlist entry. The spec needs an answer — either resolve refs loosely (game + time wins, name is advisory) or stamp real IDs onto rows. Loose resolution is cheaper and needs no sheet migration.
